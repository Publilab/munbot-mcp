# 1. LEVANTAMIENTO DE INFORMACIÓN (TRÁNSITO) PARA CREAR BASES DE DATOS RELEVANTES

- [ ]  Definir el **universo Tránsito v1** (temas/trámites incluidos):    
    - [.] Licencia de conducir (renovación/requisitos/horas)        
    - [ ] Permiso de circulación        
    - [ ] Señalización / semáforos / demarcación (ojo con cruce con reclamos)        
    - [ ]SR Estacionamientos / parquímetros (si aplica)
        
- [ ]  Construir **inventario de fuentes oficiales** (documentos y links):    
    - ordenanzas, instructivos, procedimientos, comunicados, páginas oficiales        
    - vigencia/fecha de última actualización por fuente
    
- [ ]  Taller(es) de levantamiento con contraparte Tránsito:    
    - preguntas frecuentes reales        
    - casos borde (lo que típicamente “rompe” la atención)        
    - qué cosas **NO** responderá MunBot (bordes y derivaciones)
        
- [ ] Extraer el **Top de demanda real**:    
    - top 50 preguntas reales (2 semanas) o, si no existe histórico, top 50 por criterio experto + validación
        
- [ ] Definir **tono institucional** y política de respuesta:    
    - respuestas breves, trazables, sin inventar        
    - cuando no hay fuente: “no disponible” + canal oficial
        
**Entregable tangible de esta etapa**

- [ ] Inventario de fuentes + Top 50 + lista de bordes aprobada por Tránsito.

# 2. CONSTRUCCIÓN DE BASES DE DATOS Y ARCHIVOS QUE ALIMENTEN LAS RESPUESTAS

- [ ] Crear el **Catálogo canónico de trámites** (estructura obligatoria):    
    - id_tramite, nombre_canónico, aliases, descripción, requisitos, pasos, plazos, canales, costos (si aplica), bordes, fuente, vigencia
        
- [ ] Construir la **FAQ DB (Q/A)** con campos mínimos:    
    - id_faq, pregunta_canónica, variantes (utterances), respuesta_oficial, fuente, tags (tema/trámite), vigencia, última revisión, owner_aprobador
        
- [ ] Construir **Matriz de cobertura Top 50**:    
    - pregunta → ¿tiene respuesta? → tipo (FAQ/derivación) → fuente → estado (validada/no)
        
- [ ] Definir y poblar **Diccionario de términos/aliases ciudadanos**:    
    - sinónimos (“permiso”, “permiso circulación”, “PC”), jerga local, faltas típicas
        
- [ ] Versionado y gobernanza de contenido:    
    - control de cambios (quién cambió qué, cuándo, por qué)        
    - workflow “draft → revisión → aprobado”
        
- [ ] Preparar estructura para indexación semántica (si aplica desde ya):    
    - chunks/metadata por FAQ y documento (tema, trámite, vigencia)
        

**Criterio de aceptación recomendado (para pasar a producción estable)**

- [ ] KB/FAQ cobertura ≥ 70% del Top 50 (≥ 35/50 con respuesta validada y fuente).

# 3) ACCIONES EN EL CÓDIGO (PARA QUE FAQ FUNCIONE REALMENTE EN PRODUCCIÓN)

- [ ]  Loader/ingesta de FAQ DB con:    
    - ids estables, metadata, vigencia        
    - validación de esquema (si falta fuente o vigencia, no pasa)
        
- [ ] Routing determinista: detectar que es FAQ (vs agenda/interpretativa) con reglas de alta precisión    
- [ ] Módulo de búsqueda FAQ:    
    - fase 1 mínima: coincidencia semántica (o lexical + aliases)        
    - fase 2 opcional: embeddings + top-k (y rerank si es necesario)
        
- [ ] **Confidence gating** para FAQ:    
    - umbral alto → responde        
    - umbral medio → desambiguación (2–3 opciones)        
    - umbral bajo → fallback informativo (sin inventar)
        
- [ ] Logging trazable:    
    - pregunta, intent/app, score, doc/faq_id usado, resultado (resuelto/fallback), feedback
        
- [ ] Caching:    
    - cachear respuestas FAQ comunes (reduce latencia y costo)
        
- [ ] Feature flags:    
    - rerank on/off, top-k, modo “FAQ-only” bajo carga
