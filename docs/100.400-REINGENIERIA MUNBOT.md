# **OBJETIVOS**

1. Estructurar **MunBoT** en una estructura funcional escalable de acuerdo al tamaño y estructura de las instituciones.
2. Integrar un mecanismo de `ML` para la identificación y clasificación de `intents`.
3. Investigar la posibilidad de integrar `RAG` en análisis de documentos para generar respuestas
4. Diseñar un método de participación ciudadana interactivo e intuitivo hacia la ciudadanía
5. Diseñar un método para agendar horas

# **0. ESTRUCTURA MUNBOT**

## 0.1. PROPUESTA DE ORDEN POR APPS (FUNCIONES)

- Definir “app” como unidad funcional (FAQ, Interpretativas, Reclamos, Agenda) y mover su lógica y configuración a módulos aislados con una interfaz común (intent → handler → respuesta/acción).
- Centralizar lo compartido en un “core” liviano (router, contexto, auditoría, telemetría) y cargar apps por registro; hoy ya hay un registro parcial en intents_registry.json y un umbral semántico en router_config.json.
- Estructura sugerida (conceptual) para separar app/departamento/trámite:

```text
apps/
  faq/
    kb/<departamento>/*.json
    intents.yml
    handlers.py
  interpretativas/
    kb/<departamento>/*.json
    intents.yml
    handlers.py
  reclamos/
    service/  (apunta a services/complaints-mcp)
    intents.yml
  agenda/
    service/  (apunta a services/scheduler-mcp)
    intents.yml
core/
  router/
  context/
  telemetry/
```

- Para departamentos, usar subniveles dentro de cada app: apps/ [ app]/kb/ [ departamento] y mapear trámites por metadata (categoria/depto) en lugar de mezclar todo en un único archivo grande.
- Mantener microservicios como “apps externas” y definir un contrato estándar (tools + schema + errores), así se escala a nuevas apps sin tocar el core.

## 0.2. MECANISMO `ML`

### Objetivo

Integrar ML en MunBot **sin perder control determinista**: el orquestador mantiene el “timón” (ruteo, validadores, estados de formulario y fallbacks), mientras que ML aporta **robustez lingüística** (variaciones, sinónimos, errores ortográficos, lenguaje coloquial) y mejor recuperación de información.

### Qué aporta ML en el diseño actual

- **Clasificación jerárquica (en modo gobernado):**
  - La clasificación *oficial* de MunBot sigue siendo determinista (Modelo 1 y Modelo 2), pero puede complementarse con un clasificador ML en **modo sombra** (shadow mode) para medir mejoras y capturar casos difíciles sin alterar el comportamiento del piloto.
- **Búsqueda semántica (embeddings + re-ranking):**
  - Recuperación top‑k sobre KB y “caché semántico” de respuestas validadas.
  - Reordenamiento con re‑ranker para mejorar precisión y habilitar umbrales de confianza.
- **RAG híbrido y controlado (sin dependencia permanente de LLM):**
  - En producción, la respuesta se construye desde fuentes recuperadas (KB/caché) con plantillas y trazabilidad.
  - El LLM, si se usa, se restringe a triage/etiquetado offline y/o a “cold start” bajo aprobación, para luego consolidar respuestas validadas.
- **Extracción de entidades operacionales (NER/slot filling) + validación determinista:**
  - Entidades críticas (RUT, email, teléfono, fechas) se **validan con reglas**; ML ayuda a capturar variantes naturales (“mañana en la tarde”, “cerca de…”, “hace 4 años”).
  - Entidades operacionales (ubicación, categoría, motivo, restricciones) mejoran formularios y ruteo.
- **Dataset continuo desde logs (mejora continua):**
  - Fallbacks, baja confianza, desambiguaciones fallidas y feedback negativo alimentan una cola de mejora.
  - Entrenamiento en batch con versionado, evaluación y despliegue controlado.
- **Confidence gating:**
  - Umbrales explícitos en clasificación, retrieval y extracción de entidades para evitar respuestas erróneas; ante duda se desambigua o se deriva.

### Scope

**In**
- Clasificación jerárquica app → departamento/trámite (determinista + ML en sombra).
- Búsqueda semántica top‑k + re‑ranker con umbrales.
- Interpretativas con recuperación + respuesta controlada y trazable.
- NER/slot filling para entidades operacionales + validadores actuales.
- Pipeline de datos y ciclo de entrenamiento continuo con releases gobernados.

**Out**
- Generación libre sin grounding.
- Auto‑entrenamiento 100% automático sin revisión/validación.
- “Auto‑edición de código” en tiempo real desde producción.

### Files & entry points (puntos de integración)

- **`orchestrator.py`**: ruteo, estados de conversación y decisión final (fallbacks incluidos).
- **`intent_audit.py`**: registro estructurado de decisiones, scores, fuentes y outcome.
- **`intent_regresion.json`**: dataset base para evaluación y pruebas de regresión.
- **KB por app/departamento** (`apps/*/kb/*`): fuentes trazables (FAQ/Interpretativas).
- **Logs operativos**: materia prima del dataset continuo (con redacción de PII).

### Cambios mínimos de datos (modelo de interacción)

- **`interactions`**: texto, canal, app, intent, depto/trámite, scores, respuesta/outcome, fuentes (IDs), versión de modelo/KB.
- **`labels`**: etiqueta humana (o pseudo‑label), estado (pendiente/validado), fecha, versión.
- **`feedback`**: útil/no útil, escalamiento, resolución, observaciones.

### Requisitos no negociables

- Mantener rutas determinísticas y validadores como “última palabra”.
- Trazabilidad: input → decisión → fuentes → respuesta.
- Privacidad: redacción de PII y control de retención antes de entrenar.
- Reentrenamiento reproducible y versionado (datasets + métricas).


## 0.3. LLM OPTIONS

MunBot puede operar sin LLM en producción. Si se decide incorporar un LLM (sobre todo para triage/etiquetado offline, apoyo a consolidación de respuestas o casos controlados), la selección debe considerar:

- **Disponibilidad y límites de tasa:** los “free tiers” cambian con frecuencia y pueden saturarse en periodos de alta demanda.
- **Latencia:** para WhatsApp u otros canales sin tolerancia a espera, la latencia define la experiencia.
- **Control y trazabilidad:** si el LLM redacta, debe hacerlo **solo desde evidencia recuperada** (KB) y con formato controlado.
- **Costo real:** aunque el modelo sea gratuito, el cómputo/hosting puede ser el costo dominante.

### Alternativas típicas (si se opta por SaaS en etapas acotadas)

- **Groq Cloud (free tier):**
  - Ventaja: latencia muy baja para modelos populares.
  - Riesgo: límites de tasa y cambios de política; requiere plan de contingencia.
- **Google Gemini (free tier):**
  - Ventaja: buen rendimiento general y tooling robusto.
  - Riesgo: límites y cambios del tier; no debe ser un punto único de falla.

**Recomendación operativa:** en piloto, priorizar que el flujo determinista + búsqueda semántica funcione sin LLM en producción. Incorporar LLM solo donde agregue valor claro (offline o bajo feature flags), con métricas y rollback.

### LLMs Open-Source (Gratuitos) Alternativos a Gemini

Esta sección no es un “requisito” del diseño: MunBot puede operar sin LLM. Sin embargo, si se decide incorporar un LLM (principalmente para triage offline o tareas asistidas), existen alternativas gratuitas en términos de licenciamiento de pesos/modelos. Importante: **“gratis” no significa “sin costo”** (hosting y cómputo siguen existiendo) y las licencias varían (no todas son OSI, pero sí de uso gratuito bajo condiciones).

#### Opciones recomendables (por disponibilidad y ecosistema)

- **Qwen2.5 Instruct (Alibaba):** familia fuerte en razonamiento y buen desempeño multilingüe; suele ser eficiente en tamaños 7B–14B.
- **Gemma 2 / Gemma (Google):** modelos ligeros y prácticos para despliegues locales; buena adherencia a instrucciones.
- **Mistral / Mixtral (Mistral AI):** opciones eficientes; Mixtral (MoE) destaca en calidad, a costa de complejidad operativa.
- **Llama 3.x Instruct (Meta):** muy usados y con buen soporte de tooling; revisar licencia de comunidad.
- **Phi-3.x (Microsoft):** modelos pequeños con buen rendimiento relativo; útiles cuando la infraestructura es limitada.

#### Recomendación de uso en MunBot (alineada al diseño)

- **Producción (ciudadanía):** no depender del LLM para “inventar” respuestas. Priorizar:
  - respuesta determinista desde KB/caché semántico,
  - respuesta interpretativa basada en evidencia (extractiva/plantillas),
  - desambiguación y escalamiento cuando falte certeza.
- **Offline / mejora continua:** usar LLM para:
  - triage y propuesta de etiquetas en casos nuevos,
  - sugerencia de respuesta canónica desde evidencia,
  - apoyo a curación de KB (resúmenes internos para editores, no para ciudadanía).

La selección final debe considerar: desempeño en español, costo de inferencia, facilidad de despliegue, licencias y gobernanza.

#### Consideraciones Finales

La reingeniería propuesta transforma a MunBot en un sistema híbrido **controlado y escalable**: mantiene el ruteo determinista y los formularios como columna vertebral (Agenda/Reclamos), incorpora búsqueda semántica robusta para consultas informativas, y añade ML donde realmente aporta (robustez lingüística, entidades operacionales y reducción de fricción).

Los principios que deben mantenerse en todo el diseño son:

- **Control institucional:** el bot no “se inventa” la respuesta; opera desde KB, respuestas validadas y validadores deterministas.
- **Trazabilidad:** cada decisión debe poder explicarse (ruta, scores, fuentes, versiones).
- **Gobernanza de cambios:** entrenamiento offline, releases controlados, rollback.
- **Aprendizaje útil:** el sistema mejora capturando fallos reales, consolidando respuestas validadas (caché semántico) y reforzando modelos con datos del uso.

Si se incorpora un LLM, su papel debe ser **acotado y gobernado** (triage offline y apoyo a consolidación), evitando que la operación ciudadana dependa de generación libre. En un entorno municipal, la estabilidad y la auditabilidad valen más que “parecer inteligente”.

# **1. INTENTS DETERMINISTICO - CLASIFICACIÓN JERÁRQUICA DE INTENCIONES**


MunBot organiza sus intenciones en una jerarquía de dos niveles para reducir errores y escalar a más departamentos sin complejidad explosiva. En el diseño actual, **Modelo 1 y Modelo 2 son deterministas** (ruteo y selección de flujo); ML puede añadirse como refuerzo en modo sombra y para recuperación semántica (especialmente en FAQ/Interpretativas).

## 1.1. MODELO 1: SELECCIÓN DE APP 
(FAQ / Interpretativa / Reclamo / Agenda)

**Propósito:** decidir la “aplicación” o tipo de flujo que debe manejar la consulta.

- **Reclamo:** se activa por señales explícitas (léxico de queja/denuncia, verbos de reporte, tono de disconformidad) y por contexto conversacional (si el usuario venía en flujo de reclamo).  
  - Una vez activado, el chatbot entra a un **formulario guiado** (slots) para capturar categoría, ubicación, descripción, evidencia y datos de contacto.
- **Agenda:** se activa por señales explícitas de agendamiento (reservar hora, pedir cita, agendar atención) y por contexto (usuario ya estaba agendando).  
  - Una vez activado, el chatbot entra a un **formulario guiado** para capturar motivo, fecha/ventana, datos de contacto y validaciones.
- **FAQ / Interpretativa:** si no se activan Reclamo o Agenda, la consulta se trata como “consulta de información” y se deriva a recuperación semántica.  
  - **FAQ** cubre preguntas frecuentes con respuestas canónicas o ya consolidadas (incluida la caché semántica de respuestas validadas).  
  - **Interpretativa** aplica cuando se requiere recuperar fragmentos y componer una respuesta desde KB (normativa, requisitos, procedimientos), con control y trazabilidad.

**Nota de robustez:** puede existir un clasificador ML multiclasificación (app) en **modo sombra** para medir errores y sugerir ajustes de umbrales/reglas, sin cambiar la decisión oficial en producción durante el piloto.

![[DIAG-002 1.png]]

## 1.2. MODELO 2: SELECCIÓN DE DEPARTAMENTO/ TRÁMITE 
(sub‑ruteo dentro de la app)

**Propósito:** una vez definida la app, seleccionar el “scope” correcto (departamento/trámite) y el handler correspondiente.

- **En Reclamos:** Modelo 2 selecciona el **tipo/categoría** (por ejemplo, aseo, alumbrado, ruidos, tránsito) y con ello el **esquema de formulario** y/o destino interno.
- **En Agenda:** Modelo 2 selecciona el **servicio o trámite** que se agenda (por ejemplo, licencias, permisos, atención social) y con ello el calendario/slots específicos.
- **En FAQ/Interpretativas:** Modelo 2 determina el **departamento/trámite** para restringir la búsqueda semántica al subconjunto correcto de KB y mejorar precisión (evita que una consulta de tránsito busque en ayudas sociales).

**Implementación práctica:** aunque el ruteo sea determinista, para FAQ/Interpretativas el sub‑ruteo se apoya naturalmente en la **búsqueda semántica** (embeddings + re‑ranking) y en metadata por departamento/trámite.

Resultado: Modelo 1 define el “camino” y Modelo 2 define el “contexto operativo” (handler + KB + formulario), manteniendo trazabilidad y permitiendo escalar por departamentos sin reescribir el core.

# **2. BÚSQUEDA SEMÁNTICA CON EMBEDDINGS + RE-RANKING**


Una vez que MunBot identifica que la consulta requiere recuperar información (FAQ o Interpretativa), el desempeño depende de la calidad de la búsqueda en la Base de Conocimiento (KB) y en el repositorio de respuestas validadas. Para ello se implementa una búsqueda semántica de dos fases: **Retrieve (embeddings) + Re‑rank (cross‑encoder)**, con umbrales de confianza y fallback determinístico.

## 2.1. INDEXACIÓN SEMÁNTICA (VECTOR DB + METADATA)

- **Unidad de indexación:** fragmentos cortos (párrafos / bloques) y objetos Q/A validados.
- **Embeddings:** convertir cada fragmento en un vector numérico (por ejemplo, 384 dimensiones) usando un modelo multilingüe adecuado para español.
- **Vector DB:** almacenar vectores y metadata (app, departamento, trámite, fuente, fecha, versión).  
  - La metadata permite filtrar por app/departamento antes de buscar, reduciendo ruido.

## 2.2. RECUPERACIÓN INICIAL (RETRIEVE: TOP-K)

- La consulta del usuario se transforma en embedding.
- Se consulta el índice vectorial para recuperar los **top‑k** candidatos más cercanos (similitud coseno).
- Resultado: un conjunto de candidatos “semánticamente relacionados” (cobertura amplia).

## 2.3. RE-RANKING (PRECISIÓN FINAL)

- Un **cross‑encoder** evalúa pares *(pregunta, candidato)* y asigna un score de relevancia más preciso.
- Se reordena el top‑k inicial y se seleccionan los mejores 1–3 fragmentos (o Q/A) para responder.

## 2.4. UMBRALES DE CONFIANZA Y DECISIONES DE RUTEO

Definimos un umbral explícito sobre el score del re‑ranker:

- **Score alto:** el bot responde usando el candidato ganador.
  - Prioridad: si el candidato es una **respuesta validada** (caché semántico), se responde directo (determinista).
  - Si el candidato es un fragmento de KB, se pasa al módulo interpretativo para construir respuesta desde fuentes (sin inventar).
- **Score medio / empate cercano:** activar desambiguación:
  - ofrecer 2–3 opciones (“¿Te refieres a A o B?”) o pedir un dato faltante.
- **Score bajo:** fallback gobernado:
  - pedir reformulación,
  - derivar a humano,
  - o usar reglas/FAQ exacta si existe coincidencia fuerte.

## 2.5. FALLBACK A REGLAS (GARANTÍA DE NO DEGRADACIÓN)

Si la vía semántica no alcanza confianza, MunBot no debe improvisar. Antes del fallback final, se puede intentar:

- coincidencias determinísticas (regex/palabras clave) ya existentes,
- búsqueda lexical (BM25) como respaldo,
- o navegación guiada (“selecciona tema/departamento”).

### 2.6. RESULTADO OPERACIONAL

Este módulo entrega al orquestador:

- candidatos recuperados (IDs + texto + metadata),
- scores (retrieve + rerank),
- decisión sugerida (responder / desambiguar / fallback),
- trazabilidad para auditoría.

Esta búsqueda semántica es el “motor” para FAQ e Interpretativas, y es el componente que más reduce sensibilidad a sinónimos, reformulaciones y errores ortográficos.

# **3. PREGUNTAS INTERPRETATIVAS CONTROLADA CON RAG**


## PROPÓSITO

Resolver **preguntas interpretativas** (no meramente Q/A estáticas) recuperando evidencia desde la KB y construyendo una respuesta **controlada y trazable**, evitando alucinaciones. El diseño aquí es un **RAG híbrido**: usa retrieval como base, y reduce el uso de generación libre mediante dos estrategias:

1) **Construcción de respuesta basada en evidencia** (plantillas + extracción), y  
2) **Consolidación posterior**: cuando una pregunta se valida, se transforma en una respuesta reutilizable (caché semántico), de modo que futuras consultas no requieran generación.

## 3.1. RECUPERACIÓN DE EVIDENCIA 
(entrada desde el paso 2)

El módulo recibe los fragmentos/QAs más relevantes (top 1–3) ya re‑rankeados, incluyendo:
- texto exacto de referencia,
- metadata (fuente, departamento/trámite, fecha, versión),
- score de relevancia.

## 3.2. COMPOSICIÓN DE RESPUESTA SIN DEPENDENCIA PERMANENTE DE LLM

En producción, la respuesta se construye con reglas claras:

- **Caso A: match a respuesta validada (caché semántico)**
  - Se devuelve la respuesta canónica directamente (con trazabilidad).
- **Caso B: match a fragmentos de KB (normativa/procedimiento)**
  - Se aplica una plantilla institucional controlada, por ejemplo:
    - “Según la información oficial disponible, {síntesis}…”
    - “Requisitos / pasos / plazos: …”
  - La **síntesis** se construye de forma conservadora:
    - selección de frases relevantes (sentence selection),
    - extracción de spans (modelo extractivo QA) cuando aplique,
    - normalización de listas (requisitos/pasos) si la KB ya está estructurada.
  - Regla: **no agregar contenido que no esté en la evidencia**.

## 3.3. TRAZABILIDAD Y 'RESPUESTA AUDITABLE'

Cada respuesta interpretativa debe registrar:
- IDs de los fragmentos/QAs usados,
- scores,
- versión de KB/caché,
- ruta tomada (responder/desambiguar/fallback).

Opcionalmente, la UI puede exponer “fuentes” al ciudadano (“Esta respuesta se basa en…”) para aumentar confianza.

## 3.4. MANEJO DE INCERTIDUMBRE (CUANDO LA EVIDENCIA NO ALCANZA)

Si la evidencia recuperada es insuficiente (score bajo o documentos contradictorios):

- activar desambiguación (pregunta aclaratoria),
- o declarar explícitamente limitación y derivar (“No encuentro información oficial suficiente para responder con precisión; puedo derivarte…”).

Esto es preferible a responder mal.

## 3.5. ROL ACOTADO DEL LLM (OFFLINE / COLD START GOBERNADO)

El LLM puede usarse **solo fuera de producción** (o bajo feature flag en casos controlados) para:

- triage/etiquetado de casos nuevos (intent candidato, entidades, alternativas),
- propuesta de redacción desde evidencia recuperada (sin inventar),
- sugerencia de Q/A canónica para revisión.

Regla: ninguna salida del LLM se promueve automáticamente. Debe validarse.

## 3.6. CONSOLIDACIÓN: DE “INTERPRETATIVA” A “RESPUESTA REUTILIZABLE”

Cuando una pregunta interpretativa:
- se repite,
- y/o recibe feedback positivo,
- y/o es validada por contraparte municipal,

se promueve a:
- una **respuesta canónica** (Q/A) con fuentes,
- indexada en la caché semántica.

Resultado: la próxima vez, el bot responde de forma determinista desde la respuesta validada, reduciendo latencia y dependencia de generación.

# **4. EXTRACCIÓN DE ENTIDADES (NER) ASISTIDA POR ML**


En MunBot, la extracción de entidades (NER/slot filling) no se limita a detectar formatos como RUT o email. Su valor principal es transformar lenguaje natural “desordenado” en datos operacionales para completar flujos y reducir errores, sin reemplazar validaciones deterministas.

## 4.1. QUÉ ENTIDADES IMPORTAN REALMENTE EN MUNBOT

**Entidades de validación dura (reglas como autoridad final):**
- RUT, email, teléfono
- fechas/horas (normalizadas) y rangos
- identificadores internos (folio, número de reclamo, etc.)

**Entidades operacionales (donde ML agrega más valor):**
- **Ubicación:** dirección, intersecciones, referencias (“frente a…”, “cerca de…”)
- **Categoría de reclamo:** alumbrado, aseo, ruidos, tránsito, seguridad, etc.
- **Severidad/urgencia:** riesgo, reiteración, emergencia
- **Evidencia:** menciones a foto/video/documento
- **Motivo de cita / trámite:** normalización a catálogo municipal
- **Restricciones de agenda:** “solo mañana en la tarde”, “no puedo viernes”
- **Atributos interpretativos:** años, continuidad, condición (“hace 4 años”, “sin salir del país”)

## 4.2. DÓNDE SE INTEGRA (Y POR QUÉ MEJORA EL SISTEMA)

- **Agenda (formulario guiado):**
  - extraer fecha/ventana, motivo, restricciones y contacto desde frases naturales;
  - reducir iteraciones (“¿puedes repetir?”) y fallos de validación.
- **Reclamos (formulario guiado):**
  - extraer ubicación, categoría, descripción mínima y evidencia;
  - enrutar a unidad correcta y mejorar calidad del ticket.
- **FAQ/Interpretativas:**
  - usar entidades como filtros/boosters para retrieval (por departamento/trámite y por parámetros relevantes).

## 4.3. ML COMO “COPILOTO” DE RUTEO Y DE ESTADO CONVERSACIONAL

Además de entidades, un modelo ML pequeño puede clasificar el **acto conversacional** del mensaje:
- responde_slot vs pregunta vs corrección vs cancelación vs cambio de tema

Esto reduce un error típico en formularios: interpretar una pregunta como si fuera el dato del campo.

## 4.4. VALIDACIÓN DETERMINISTA (CONTROL INSTITUCIONAL)

Independiente de lo que extraiga ML:
- los datos críticos pasan por validadores deterministas;
- si no validan, el bot repregunta o guía (no “fuerza” el dato).

Esto preserva seguridad y trazabilidad.

## 4.5. ENTRENAMIENTO Y AUTO‑MEJORA (SIN APRENDIZAJE EN VIVO)

La fuente más potente de entrenamiento en MunBot está en sus propios flujos guiados:

- en Agenda/Reclamos, el bot sabe qué slot pedía y si la entrada validó;
- eso permite **auto-etiquetar** ejemplos positivos/negativos para NER y acto conversacional;
- los casos difíciles (fallidos o ambiguos) pasan a cola de revisión humana.

El reentrenamiento ocurre offline (batch) y se despliega con versiones controladas.

# **5. SISTEMA DE ENTRENAMIENTO CONTINUO (AUTO-MEJORA)**


Para asegurar que el rendimiento de MunBot mejore con el tiempo y se adapte a nuevas consultas ciudadanas **sin comprometer estabilidad, trazabilidad ni control institucional**, se implementará un **pipeline de mejora continua** con tres principios:

- **Evidencia en producción, aprendizaje fuera de producción:** en producción se ejecuta inferencia y registro; el entrenamiento ocurre offline (batch).
- **Gobernanza explícita:** todo cambio relevante (modelos, KB, parámetros) se valida, versiona y despliega con control y rollback.
- **Reducción progresiva de dependencia del LLM:** el LLM se usa, cuando aplica, como apoyo controlado (triage/etiquetado y/o cold start gobernado), mientras el sistema consolida respuestas validadas.

## 5.1. CAPTURA DE EVIDENCIA (LOGS → COLA DE MEJORA)

Se extraerán periódicamente:
- fallbacks y “no resolución”,
- baja confianza y desambiguaciones fallidas,
- correcciones explícitas del usuario,
- escalamiento humano,
- consultas nuevas recurrentes.

Cada caso se guarda con: texto, contexto mínimo, ruta, intent/score, resultado, metadatos y versiones.

## 5.2. PRIVACIDAD Y CALIDAD DE DATOS (OBLIGATORIO)

Antes de entrenar:
- redacción/anonimización de PII (RUT, email, teléfono, dirección, etc.),
- controles de retención y acceso por roles,
- separación de ambientes,
- versionado de datasets para auditoría.

## 5.3. CONSTRUCCIÓN DE DATASETS (HUMANO + AUTO-ETIQUETADO)

- **Etiquetado humano:** corrige intents, ruteo y entidades operacionales; define nuevos intents si corresponde.
- **Auto-etiquetado desde formularios:** Agenda y Reclamos permiten generar ejemplos positivos/negativos por slot y validador (alto valor para NER y acto conversacional).

## 5.4. TRIAGE ASISTIDO POR LLM (OFFLINE Y CON CONTROL)

Para casos nuevos o fallidos, un LLM puede:
- proponer intent candidato + alternativas,
- sugerir entidades/slots,
- proponer una redacción basada en evidencia.

Regla: no se promueve automáticamente; requiere validación (humana o pseudo‑labeling estricto).

## 5.5. REENTRENAMIENTO BATCH Y EVALUACIÓN

Se reentrenan y versionan:
- clasificador de intents (métricas: precision/recall por intent, confusión),
- extracción de entidades/slots (F1 por entidad, éxito de formulario),
- parámetros de retrieval (umbrales, top‑k, reranking).

## 5.6. EVOLUCIÓN DEL CONOCIMIENTO: KB + CACHÉ SEMÁNTICO

- Preguntas interpretativas resueltas y validadas se promueven a **Q/A canónicas** en un repositorio de respuestas validadas (caché semántico), con fuentes y metadata.
- La KB documental se actualiza cuando aparecen brechas recurrentes.

Resultado: cada vez más consultas se responden sin generación, con menor latencia y mayor consistencia.

## 5.7. PROMOCIÓN A PRODUCCIÓN SIN “AUTO‑EDITAR CÓDIGO”

Los cambios se despliegan como artefactos versionados:
- modelos,
- datasets,
- catálogos/configuración,
- KB/caché semántico,
- parámetros de umbrales.

Cambios de código: CI/CD + pruebas + revisión humana + rollout controlado.

## 5.8. MÉTRICAS ONLINE/OFFLINE Y RELEASES GOBERNADOS

- Offline: métricas por intent/entidad, retrieval, regresión.
- Online: fallback, escalamiento, desambiguación, contención, CSAT y latencia.

Toda versión pasa por staging, aprobación mínima y monitoreo post‑release con rollback.

# **6. _CONFIDENCE GATING_: MANEJO DE BAJA CONFIANZA Y DESAMBIGUACIÓN**


El “confidence gating” define decisiones explícitas cuando el sistema no está seguro. En MunBot no se trata solo de ML: también aplica a retrieval y a formularios. La regla general es simple: **si no hay confianza suficiente, no se responde como si la hubiera**.

## 6.1. GATING EN RUTEO (MODELO 1 Y MODELO 2)

- Si Reclamo/Agenda no se detectan con claridad, el bot no debe forzar un formulario.
- En FAQ/Interpretativas, si el sub‑ruteo a departamento es incierto, se puede:
  - pedir un dato (“¿Tu consulta es sobre Tránsito o Ayudas Sociales?”),
  - o mostrar 2–3 opciones.

## 6.2. GATING EN BÚSQUEDA SEMÁNTICA (RETRIEVE + RE‑RANK)

- **Score alto:** responder (priorizando Q/A validadas).
- **Score medio:** desambiguar (top 2–3 candidatos).
- **Score bajo:** fallback gobernado (reformular/derivar/humano).

## 6.3. GATING EN EXTRACCIÓN DE ENTIDADES Y FORMULARIOS

- Si un dato extraído por ML no pasa validación determinista (RUT/email/fecha), se repregunta.
- Si el acto conversacional parece “pregunta/corrección” y no “respuesta de slot”, se detiene el avance del formulario y se aclara.

## 6.4. DESAMBIGUACIÓN COMO SALIDA ESTÁNDAR (NO COMO EXCEPCIÓN)

La desambiguación debe ser breve, explícita y con salida segura:
- ofrecer pocas opciones (2–3),
- incluir “Ninguna de las anteriores”,
- y permitir volver atrás.

## 6.5. ESCALAMIENTO A HUMANO Y TRAZABILIDAD

Cuando el caso excede confianza o cobertura:
- derivar a humano o canal institucional,
- registrar decisión, scores y fuentes intentadas.

Esto protege la credibilidad del bot y evita errores institucionales.

# ANEXO C. UMBRALES DE CONFIANZA Y DESAMBIGUACIÓN (INCLUYE POLÍTICA PARA GAPS DE KB)


## C.1 PRINCIPIO RECTOR

- Bajo umbral: **no “completar” con suposiciones**.    
- Mejor una desambiguación breve o derivación informativa que una respuesta incorrecta.    

## C.2 UMBRALES PROPUESTOS

### Routing (FAQ / Interpretativa / Agenda)

- **Alta:** score ≥ 0.75 y delta ≥ 0.15 → enruta directo    
- **Media:** 0.60–0.74 o delta < 0.15 → desambiguación (2–3 opciones)    
- **Baja:** < 0.60 → 1 desambiguación; si persiste → fallback informativo    

### Retrieval KB/caché

- Definir bandas (calibrables por modelo): alta / media / baja    
- **Media:** confirmar intención o pedir dato faltante (por ejemplo “¿te refieres a plazos o requisitos?”)    
- **Baja:** derivación informativa + registrar gap    

### NER/slots

- **Alta:** ≥0.80 → aceptar y validar    
- **Media:** 0.65–0.79 → confirmar    
- **Baja:** <0.65 → repregunta guiada    

## C.3 Reglas de desambiguación

- Máximo 2 rondas    
- Ofrecer opciones (no pregunta abierta)    
- Si no se resuelve: fallback informativo + registro en cola de mejora    

## C.4 POLÍTICA DE “GAP DE CONOCIMIENTO” (PARA CONSTRUIR KB Y DB DE RESPUESTAS)

Activar “gap” cuando:
- La misma consulta/tema aparece **≥ 5 veces/semana** y cae en banda baja de retrieval, o    
- Genera feedback negativo recurrente, o    
- Activa desambiguación y aún así termina en fallback.    

Acción:
- Se crea ítem en cola KB: “tema → fuentes requeridas → responsable → fecha”    
- Se actualiza: KB / caché semántica validada / catálogo (según corresponda)    
- Se prueba en staging con regresión antes de release
