# **ESQUEMA FLUJO COMPLETO**

El viaje de la pregunta del usuario es un "embudo" que pasa por tres grandes etapas:

1. **Gateway (Entrada):** La puerta de entrada a la aplicación.
2. **MCP-Core (Orquestador):** El cerebro que decide qué hacer.
3. **LLM_Docs-MCP (Servicio de Conocimiento):** El especialista que busca y genera la respuesta.

# **PROPUESTAS DE MEJORA**

## Implementar un clasificador de intenciones primarias

Implementar un clasificador de intenciones primarias con un LLM al inicio del flujo resolvería los problemas que mencionas de la siguiente manera:

1. **Eficiencia (Coste y Tiempo):** Una única llamada a un LLM optimizado para clasificación es mucho más rápida y barata que ejecutar todo el pipeline de RAG (búsqueda en base de datos vectorial + generación de respuesta). Esta llamada inicial actuaría como un "aiguilleur" o "dispatcher" inteligente.    
   
2. **Precisión en la Intención:** Un LLM es infinitamente superior a las palabras clave para entender la verdadera intención en frases complejas.    
    - En tu ejemplo 2 (`"Hola, voy a viajar... necesito información sobre el permiso de aterrizaje."`), el LLM ignoraría el "Hola" y se centraría en "información permiso de aterrizaje", clasificándolo correctamente como una consulta de documentos.
    - En tu ejemplo 3 (`"...como puedo sacar un permiso de aterrizaje"`), el LLM puede inferir que "cómo puedo sacar" implica una solicitud de procedimiento o requisitos, una sutileza que los routers de palabras clave no captarían.
      
3. **Extracción de Entidades Temprana:** El clasificador no solo debe devolver la intención, sino también las **entidades clave** que detecta. Para la consulta sobre el permiso de aterrizaje, debería extraer:    
    - **Intención:** `consulta_documento`
    - **Entidad Principal:** `permiso de aterrizaje`
    - **Entidad Secundaria (Tema):** `requisitos` (inferido de "cuales son los requisitos")

Con esta información estructurada desde el principio, el resto del proceso se vuelve determinista y eficiente.

### **Paso 1**: Clasificación de Intención y Extracción de Entidades (LLM)

- **Acción:** El `orchestrator` recibe la consulta y su **primera y única acción inicial** es llamar a una nueva función, digamos `classify_intent_and_entities(user_input)`.
- **Prompt (Quemado en el código o en un archivo `classify-main_intent.txt`):**
    
    ```
    Eres el cerebro de un chatbot de servicios municipales. Tu trabajo es clasificar la intención del usuario y extraer las entidades clave. Responde únicamente con un objeto JSON.
    
    Las intenciones posibles son: "consulta_documento", "agendar_cita", "registrar_reclamo", "saludo", "despedida", "pregunta_casual", "no_entendido".
    Las entidades clave son: "tramite", "departamento", "tema_especifico".
    
    Usuario: "Hola, como estás?"
    JSON: {"intencion": "saludo", "entidades": {}}
    
    Usuario: "Quiero agendar una cita para mañana a las 10"
    JSON: {"intencion": "agendar_cita", "entidades": {"fecha": "mañana", "hora": "10"}}
    
    Usuario: "cuales son los requisitos para el permiso de aterrizaje"
    JSON: {"intencion": "consulta_documento", "entidades": {"tramite": "permiso de aterrizaje", "tema_especifico": "requisitos"}}
    
    Usuario: "{{AQUÍ VA LA CONSULTA DEL USUARIO}}"
    JSON:
    ```
    
- **Resultado de este paso:** El LLM devuelve un objeto JSON:
    
    ```json
    {
      "intencion": "consulta_documento",
      "entidades": {
        "tramite": "permiso de aterrizaje",
        "tema_especifico": "requisitos"
      }
    }
    ```

### **Paso 2**: Enrutamiento Basado en la Intención Clasificada

- **Acción:** El `orchestrator` ahora tiene una intención clara y estructurada. Usa una simple estructura `if/elif` o un diccionario de manejadores para dirigir el flujo.
    
    ```python
    # mcp-core/orchestrator.py (versión mejorada)
    
    clasificacion = classify_intent_and_entities(user_input)
    intencion = clasificacion.get("intencion")
    
    if intencion == "consulta_documento":
        # Llama a la función especializada en RAG
        return handle_document_query(clasificacion["entidades"])
    elif intencion == "agendar_cita":
        # Llama al flujo de agendamiento
        return handle_scheduler_flow(clasificacion["entidades"])
    elif intencion == "saludo":
        return {"respuesta": "¡Hola! ¿En qué puedo ayudarte?"}
    # ... etc.
    ```


> **IMPORTANTE**:
> Hay 4 modulos de consulta especializada que pueden ser redirigidos desde la función `classify_intent_and_entities`
> 	1. `RAG-faq.json` ▶️ Preguntas genéricas y frecuentes
> 	2. `RAG-depto_info.json` ▶️ Información esencial de los distintos departamentos 
> 	3. `RAG-doc_tramites.json` ▶️ Información de los trámites para obtener documentación oficial
> 	4. `RAG-Ayudas_Sociales.json`| `RAG-Ayudas_Sociales.json` | `RAG-Horario_Comercio.json` | `RAG-Horario_Comercio.json` ▶️ Información sobre temáticas legisladas y oficiales del Gobierno de Curoscant
> 	5. Hay que sumarlo dos procesos más que son  `Complaint-MCP` y `Scheduler-MCP` encargado de registrar reclamos y agendar horas respectivamente.
> El `if` debe dirigir hacia estos cuatro modulos RAG para estructurar la respuesta. Tareas 
> 		- Organizar los json para hacer más eficiente la interacción
> 		- Recrear todas las posibles interacciones para configurar el prompt y señalar las palabras claves
> 		- Averiguar si existen mecanismo en el RAG para estructurar respuestas combinadas a interacciones tipo. Es decir, por ejemplo, si el USER hace la siguiente interacción `Estoy pronto a llegar a Curoscant y necesito saber como puedo sacar el pemiso de aterrizaje`, la solicitud del USER requiere una lógica de construcción de la respuesta por lo que el BOT debe reconocer distintas alternativas de respuesta para los distintos módulos según los distintos tipos de consultas:
> 			- Direct Question ▶️ El USER hace una consulta que hace match directo o con una pregunta contenida tal como fue escrita en FAQ, una etiqueta en un json [por ejemplo en la etiqueta alias], o la respuesta está contenida en la etiqueta `texto` 
> 			- Non Direct Question ▶️ El USER puede hacer una consulta que identifica el nombre del proceso o documento [permiso de antecedentes, medio ambiente, comercio, departamento de transporte interestelar], pero no específica que tipo de información específica, es decir la información que el USER espera sea devuelta por el BOT [dirección email, nombre encargado, requisitos]. En este caso el BOT al identificar la ausencia de los 2 elementos básicos identificables en la interacción del USER para elaborar una respueta, el BOT debe requerir el otro elemento para elaborar la respuesta.
> 				- _caso_: Si en el mensaje [m] del user solo está contenido solo un elemento de identificación de contexto para elaborar la respuesta
> 				  `if o ∈ m ∧ i ∉ m`
> 				  `if o ∉ m ∧ i ∈ m`
> 			- Combined Layer ▶️ En este caso la interacción del USER es específica pero contiene más de una etiqueta a consultar y esta puede ser el objeto [o] o la información [o]. 
> 			  _ej._: 
> 				  - Que puedo hacer para sacar el permiso de aterrizaje ▶️ En este caso el BOT identifica el objeto [o] pero no puede identificar la etiqueta desde donde debe extraer la información [i]. Según el caso descrito anteriormente, si el BOT no logra identificar la etiqueta, el BOT debería pedir la específicación, pero al contener la frase `Qué puedo hacer` el BOT debe identificarlo como una respuesta que contiene varías etiquetas. Para este ejemplo la respuesta debería contener `"seccion": "donde_obtener"`, `"seccion": "requisitos"` y `"seccion": "horario_atencion"` [Para obtener el permiso de aterrizaje debes dirigirte a Departamento de Tránsito Aéreo (Edificio Consistorial Coruscant, nivel 5143), y debes llevar contigo tu Licencia de transporte, identificación planetaria, plan de ruta, formulario 77 completo y la evaluación de seguridad de la nave. Recuerda que nuestros horarios de atención es Lunes a viernes, 08:00 – 17:00]. Se entiende que ha interacciones que requieren una construcción más compleja en su respuesta al ser tomada como un proceso, por lo que no se si hay técnicas en RAG que permitan identificació de interacciones para estructurar estas respuestas.
> 			- Combined Specified Layer ▶️ En este caso el USER puede hacer dos consultas combinadas en una misma interacción que cumplen con la formula para generar una respuesta [m = o + i] por ejemplo `Quiero saber los requisitos para obtener el permiso de aterrizaje y la dirección donde debo trámitarlo` en este ejemplo podemos advertir que la interacción del user podría traducirse en 2 requerimientos en una misma interacción es decir: `permiso de aterrizaje` [o] + `donde_obtener`  ∧ `permiso de aterrizaje` + `requisitos`. Se entiende que en una misma interacción el BOT puede identificar [o] > 1 o [i] > 1 en una misma interacción.


#### Arquitectura Híbrida y por Fases

La solución más robusta y que mejor se adapta a nuestro proyecto es una **combinación sinérgica** de varias de tus propuestas. No debemos verlas como opciones excluyentes, sino como capas de una misma arquitectura.

La combinación ideal para nosotros es: **Router de Intenciones + Query Rewriting → RAG Multi-etapa (Retrieve/Rerank) → Plan-then-Generate → Structured Generation**

Vamos a desglosar por qué esta combinación es tan potente:

1. **Router de Intenciones y Dominios (Punto de Partida):**
    
    - **Qué es:** Es exactamente la arquitectura que ya acordamos. El `[orchestrator.py](code-assist-path:./mcp-core/orchestrator.py "./mcp-core/orchestrator.py")` primero clasifica la intención y las entidades.
    - **Por qué es fundamental:** Es el "cerebro" que dirige el tráfico. Sin esto, todas las demás optimizaciones RAG trabajarían sobre ruido. Nos permite enviar la consulta `permiso de aterrizaje` al "sub-RAG" de trámites y no al de ayudas sociales, mejorando drásticamente la relevancia desde el primer paso.
2. **Query Rewriting y Expansión de Alias (Mejora de la Entrada):**
    
    - **Qué es:** Antes de buscar, enriquecemos la consulta del usuario. `permiso aterrizaje` se expande a `(permiso de aterrizaje, licencia de vuelo, autorización de llegada)`.
    - **Por qué es clave:** Ataca directamente el problema de los sinónimos y la variedad del lenguaje humano. Es una mejora de bajo costo y alto impacto que aumenta enormemente las posibilidades de encontrar los documentos correctos (recall).
3. **RAG Multi-etapa con Reranking (Mejora de la Recuperación):**
    
    - **Qué es:** No nos conformamos con la primera búsqueda. Primero, recuperamos una lista amplia de posibles fragmentos (Retrieve), y luego usamos un modelo más potente y preciso (un cross-encoder) para reordenar solo los mejores candidatos (Rerank).
    - **Por qué es superior:** Es el estándar de oro para la precisión en RAG. La primera búsqueda (híbrida con BM25 + vectores) asegura que no nos perdamos nada importante. El reranking garantiza que el contexto que pasamos al LLM final sea de la más alta calidad posible, reduciendo el ruido y las alucinaciones.
4. **Planificación de Respuesta (Plan-then-Generate) (Inteligencia en la Composición):**
    
    - **Qué es:** Para preguntas complejas como `¿Qué necesito para sacar el permiso?`, el sistema no genera una respuesta directamente. Primero, genera un "plan": `["buscar requisitos", "buscar donde_obtener", "buscar horario"]`.
    - **Por qué es el salto cualitativo:** Resuelve elegantemente tus casos de uso `Combined Layer` y `Combined Specified Layer`. Permite al bot razonar sobre qué piezas de información constituyen una respuesta completa y luego ir a buscarlas de forma dirigida.
5. **Generación Estructurada con Contrato JSON (Mejora de la Salida):**
    
    - **Qué es:** Forzamos al LLM a que su respuesta final no sea texto libre, sino un JSON predecible: `{"requisitos": "...", "direccion": "...", "horario": "..."}`.
    - **Por qué es crucial para un producto robusto:**
        - **Fiabilidad:** La salida es consistente y predecible.
        - **Testabilidad:** Podemos escribir pruebas unitarias que verifiquen las claves del JSON.
        - **Cacheo:** Es trivial cachear respuestas si la salida es un objeto determinista.
        - **Integración:** El frontend (o cualquier otro servicio) puede consumir estos datos de forma segura sin necesidad de parsear texto.

---
### **Paso 3**: Ejecución del Manejador Especializado (RAG Inteligente)

- **Acción:** Se ejecuta la función `handle_document_query` con las entidades ya extraídas.
- **Lógica Interna:**
    1. Usa la entidad `tramite: "permiso de aterrizaje"` para buscar en la base de datos vectorial (Qdrant) y recuperar todos los fragmentos de texto relacionados con ese trámite.
    2. Usa la entidad `tema_especifico: "requisitos"` para filtrar aún más esos fragmentos o para darle una instrucción más precisa al LLM de generación.
    3. Llama al LLM de **generación de respuestas** (usando el prompt `[doc-generar_respuesta_llm.txt](code-assist-path:./mcp-core/prompts/doc-generar_respuesta_llm.txt "./mcp-core/prompts/doc-generar_respuesta_llm.txt")`) con el contexto recuperado y la pregunta original.
    4. El LLM genera la respuesta final y precisa.

---

**En conclusión, tu análisis es perfecto.** El sistema se beneficiaría enormemente de adoptar este enfoque "primero clasificar, luego actuar". Sería más rápido, más barato, más preciso y el código del orquestador se volvería mucho más limpio y fácil de mantener.

## Estrategia en fase de identificación de intents

### **Paso 1**: Clasificación de Intención y Entidades (El "Cerebro" Central)

Esta es la pieza clave y el cambio más importante.
- **Por qué es correcto:** Mover la clasificación al inicio del todo tiene ventajas masivas:    
    1. **Eficiencia de Costos y Tiempo:** Reemplazas múltiples llamadas a RAG (potencialmente costosas y lentas) con una única llamada a un LLM optimizado para clasificación, que es mucho más rápida y barata.
    2. **Precisión:** Un prompt diseñado específicamente para clasificar la intención y extraer entidades será mucho más preciso que intentar inferirlo a través de búsquedas de similitud en una base de datos vectorial.
    3. **Centralización de la Lógica:** Toda la "comprensión" inicial del input del usuario ocurre en un solo lugar, haciendo el resto del sistema más simple y predecible.
- **Sobre tu nota "IMPORTANTE":** Tienes toda la razón. Para que el clasificador sea efectivo, su prompt debe ser "consciente" del conocimiento que el bot posee. Podemos crear un script simple que recorra los archivos JSON (`[RAG-faq.json](code-assist-path:./llm_docs-mcp/documents/RAG-faq.json "./llm_docs-mcp/documents/faq_respuestas.json")`, `[RAG-depto_info.json](code-assist-path:./llm_docs-mcp/documents/RAG-depto_info.json "./llm_docs-mcp/documents/RAG-depto_info.json")`, etc.) y extraiga palabras clave, nombres de trámites y secciones para construir un prompt de clasificación más robusto y dinámico.
    
### **Paso 2**: Enrutamiento Basado en Intención (El "Panel de Control")

Una vez que tienes una intención clara, el resto del flujo se simplifica enormemente.
- **Por qué es correcto:**    
    1. **Claridad del Código:** Un `if/elif/else` o un diccionario de manejadores en `[orchestrator.py](code-assist-path:./mcp-core/orchestrator.py "./mcp-core/orchestrator.py")` es infinitamente más legible y mantenible que la lógica compleja y anidada que probablemente existe ahora.
    2. **Flexibilidad:** Añadir una nueva habilidad al bot (ej. "consultar_estado_tramite") se vuelve tan simple como añadir una nueva intención al clasificador, una nueva condición `elif` al enrutador y una nueva función `handle_status_query`.
- **Sobre los 4 módulos RAG:** El enrutador puede manejar esto perfectamente. La `intencion` principal sería `consulta_documento`, y las `entidades` extraídas (`"tema_especifico": "FAQ"`, `"departamento": "Obras"`, etc.) determinarían qué base de datos o archivo JSON específico consultar.
    
    ```python
    # mcp-core/orchestrator.py (conceptual)
    
    clasificacion = classify_intent_and_entities(user_input)
    intencion = clasificacion.get("intencion")
    entidades = clasificacion.get("entidades", {})
    
    if intencion == "consulta_documento":
        # Un sub-enrutador o lógica adicional puede elegir la fuente de RAG
        return handle_document_query(entidades) 
    elif intencion == "agendar_cita":
        return handle_scheduler_flow(entidades)
    # ... etc
    ```
    

### **Paso 3**: Ejecución del Manejador Especializado (Los "Especialistas")

Aquí es donde el RAG y otras lógicas de negocio entran en juego, pero ahora con un propósito claro.
- **Por qué es correcto:** La función `handle_document_query` ya no tiene que adivinar lo que el usuario quiere. Recibe un diccionario estructurado (`{"tramite": "permiso de aterrizaje", "tema_especifico": "requisitos"}`) y su única misión es encontrar esa información específica, lo cual es mucho más simple y fiable.


### **Paso 4**: Tipos de consulta (Direct, Non-Direct, Combined)

Tu análisis de los tipos de interacción del usuario es brillante y es exactamente el tipo de problema que esta nueva arquitectura resuelve elegantemente. Así es como cada caso sería manejado:

1. **Direct Question (Pregunta Directa):**    
    - **Ejemplo:** `Quiero saber los requisitos para el permiso de aterrizaje.`
    - **Cómo funciona:** El clasificador del **Paso 1** devolvería:
        
        ```json
        {"intencion": "consulta_documento", "entidades": {"tramite": "permiso de aterrizaje", "tema_especifico": "requisitos"}}
        ```
        
    - El manejador `handle_document_query` recibe todo lo que necesita y ejecuta la búsqueda RAG directamente. Es el caso más simple.
      
2. **Non-Direct Question (Relleno de Entidades / "Slot Filling"):**    
    - **Ejemplo:** `Necesito información sobre el permiso de aterrizaje.`
    - **Cómo funciona:** El clasificador del **Paso 1** identifica la intención y el trámite, pero no el tema específico.
        
        ```json
        {"intencion": "consulta_documento", "entidades": {"tramite": "permiso de aterrizaje"}}
        ```
        
    - El manejador `handle_document_query` ve que la entidad `tema_especifico` está ausente. En lugar de buscar en RAG, su lógica es preguntar al usuario para "rellenar el hueco".
    - **Respuesta del Bot:** `Entendido, necesitas información sobre el "permiso de aterrizaje". ¿Qué dato específico te interesa? Por ejemplo: requisitos, costo, dónde se tramita, o el horario de atención.`
      
3. **Combined Layer (Intención Implícita Múltiple):**    
    - **Ejemplo:** `¿Qué puedo hacer para sacar el permiso de aterrizaje?`
    - **Cómo funciona:** Aquí es donde la ingeniería de prompts para el clasificador del **Paso 1** se vuelve crucial. El prompt se puede instruir para que reconozca frases como "¿Qué puedo hacer...?" o "¿Cómo consigo...?" como una solicitud de un resumen del proceso.
    - El clasificador podría devolver una entidad especial:
        
        ```json
        {"intencion": "consulta_documento", "entidades": {"tramite": "permiso de aterrizaje", "tema_especifico": ["resumen_proceso"]}}
        ```
        
    - El manejador `handle_document_query` ve `resumen_proceso` y sabe que debe buscar varias piezas de información clave (ej. `requisitos`, `donde_obtener`, `costo`) y combinarlas en una respuesta coherente, tal como lo describiste.
      
4. **Combined Specified Layer (Múltiples Entidades Explícitas):**    
    - **Ejemplo:** `Quiero saber los requisitos para el permiso de aterrizaje y la dirección donde debo tramitarlo.`
    - **Cómo funciona:** Un buen LLM clasificador puede extraer múltiples entidades de una sola vez. El prompt se diseñaría para esto.
    - El clasificador del **Paso 1** devolvería un array en la entidad:
        
        ```json
        {
          "intencion": "consulta_documento",
          "entidades": {
            "tramite": "permiso de aterrizaje",
            "tema_especifico": ["requisitos", "donde_obtener"]
          }
        }
        ```
        
    - El manejador `handle_document_query` iteraría sobre la lista `["requisitos", "donde_obtener"]`, realizaría una búsqueda RAG para cada uno y luego ensamblaría una única respuesta final para el usuario.
